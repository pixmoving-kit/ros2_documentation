# 服务质量设置

<span id="overview"></span>
## 概述

ROS 2 提供了丰富的服务质量（Quality of Service，QoS）策略，可用于调整节点之间的通信行为。通过合适的 QoS 策略组合，ROS 2 既能实现类似 TCP 的可靠传输，也能采用类似 UDP 的尽力而为方式，还能在两者之间实现多种通信行为。ROS 1 主要只支持 TCP，而 ROS 2 能够利用底层 DDS 传输的灵活性，适应更适合“尽力而为”策略的有损无线网络，或需要合适 QoS 配置来满足截止时间要求的实时计算系统。

一组 QoS“策略”（policy）共同构成一个 QoS“配置”（profile）。针对具体场景选择正确的策略比较复杂，因此 ROS 2 为传感器数据等常见用途提供了一组预定义配置。同时，开发者仍可以灵活调整配置中的具体策略。

可以为发布者、订阅、服务端和客户端指定 QoS 配置。这些实体的每个实例都可以独立使用自己的配置，但不同配置之间可能不兼容，导致消息无法传递。

<span id="qos-policies"></span> <span id="about-qos-policies"></span>
## QoS 策略

目前，基础 QoS 配置包含以下策略设置：

- **历史记录（History）**
    - *保留最近样本（Keep last）*：最多只保存 N 个样本，N 由队列深度选项指定。
    - *保留全部样本（Keep all）*：保存所有样本，但受底层中间件所配置的资源上限约束。
- **深度（Depth）**
    - *队列大小*：只有当历史记录策略设为“保留最近样本”时才生效。
- **可靠性（Reliability）**
    - *尽力而为（Best effort）*：尝试交付样本，但网络不稳定时可能丢失样本。
    - *可靠（Reliable）*：保证交付样本，必要时可能重试多次。
- **持久性（Durability）**
    - *本地瞬态（Transient local）*：由发布者负责保留样本，供后加入的订阅使用。
    - *易失（Volatile）*：不尝试保留样本。
- **截止时间（Deadline）**
    - *时长*：向同一话题连续发布两条消息之间所允许的预期最大时间间隔。
- **生存时间（Lifespan）**
    - *时长*：消息从发布到接收的最大允许时间。超过该时长，消息将被视为陈旧或过期；过期消息会被静默丢弃，接收端实际上不会收到它们。
- **活跃性（Liveliness）**
    - *自动（Automatic）*：节点的任意一个发布者发布消息时，系统都会将该节点的所有发布者视为在接下来一个“租约时长”内保持活跃。
    - *按话题手动声明（Manual by topic）*：发布者通过调用发布者 API 手动声明自己仍然活跃后，系统会将其视为在接下来一个“租约时长”内保持活跃。
- **租约时长（Lease Duration）**
    - *时长*：发布者必须在此最大时间间隔内表明自己仍然活跃，否则系统会认为它已失去活跃性；失去活跃性可能意味着发生了故障。

对于所有非时长类策略，还可以选择“系统默认”（system default），即使用底层中间件的默认值。对于所有时长类策略，还可以选择“默认”（default），表示未指定时长；底层中间件通常将其解释为无限长。

<span id="comparison-to-ros-1"></span>
### 与 ROS 1 的比较

ROS 2 的历史记录策略与深度策略组合起来，提供了类似 ROS 1 队列大小的功能。

ROS 2 的可靠性策略类似于 ROS 1 中使用 UDPROS（仅在 `roscpp` 中可用）实现的尽力而为传输，或使用 TCPROS（ROS 1 默认方式）实现的可靠传输。不过，即使采用可靠策略，ROS 2 仍使用 UDP 实现，因此能够在适当情况下使用组播。

将持久性设为“本地瞬态”，并配合任意深度，就能提供类似 ROS 1 中锁存（latching）发布者的功能。其余策略在 ROS 1 中没有对应功能，因此 ROS 2 在这一方面更丰富。未来 ROS 2 还可能提供更多 QoS 策略。

<span id="qos-profiles"></span>
## QoS 配置

QoS 配置使开发者能够专注于应用本身，而不必逐一考虑所有设置。每种配置定义一组适合特定用途、能够配合使用的策略。

目前定义的 QoS 配置如下。

### 发布者和订阅的默认 QoS 设置

为了方便从 ROS 1 迁移到 ROS 2，默认设置应提供相近的网络行为。ROS 2 发布者和订阅默认采用“保留最近样本”的历史记录策略，队列大小为 10；可靠性为“可靠”，持久性为“易失”，活跃性为“系统默认”。截止时间、生存时间和租约时长均设为“默认”。

### 服务

与发布者和订阅一样，服务使用可靠传输。对服务而言，使用易失持久性尤其重要，否则重新启动的服务端可能会收到过时的请求。虽然客户端具有避免接收多个响应的保护机制，但服务端并没有防止过时请求产生副作用的保护机制。

### 传感器数据

对于传感器数据，大多数情况下及时接收读数比确保每一条读数都送达更重要。也就是说，开发者希望在采集到最新样本后尽快收到它，即使可能因此丢失部分样本。因此，传感器数据配置采用尽力而为的可靠性策略，并使用较小的队列。

### 参数

ROS 2 的参数基于服务，因此使用类似的配置。不同之处在于参数使用更大的队列深度，以避免请求丢失，例如参数客户端暂时无法连接参数服务端时。

### 系统默认

所有策略均使用 RMW 实现的默认值。不同 RMW 实现的默认值可能不同。

上述配置采用的具体策略见 [`qos_profiles.h`](https://github.com/ros2/rmw/blob/rolling/rmw/include/rmw/qos_profiles.h)。这些配置中的设置可能会根据社区反馈进一步调整。

<span id="qos-compatibilities"></span> <span id="about-qos-compatibilities"></span>
## QoS 兼容性

**说明：** 本节以发布者和订阅为例，但同样适用于服务端和客户端。

发布者和订阅可以独立配置 QoS。只有双方的 QoS 配置兼容时，才会建立连接。

QoS 配置的兼容性采用“请求与提供”（Request vs Offered）模型判断。订阅*请求*的 QoS 配置表示它愿意接受的“最低质量”，发布者*提供*的 QoS 配置表示它能够提供的“最高质量”。只有请求配置中的每一项策略都不比提供配置中的对应策略更严格，才会建立连接。多个订阅即使请求不同的 QoS 配置，也可以同时连接到同一个发布者。发布者与订阅之间的兼容性不受其他发布者和订阅的影响。

下表列出了不同策略设置的兼容性及其结果。

### 可靠性策略的兼容性

| 发布者 | 订阅 | 是否兼容 |
| --- | --- | --- |
| 尽力而为 | 尽力而为 | 是 |
| 尽力而为 | 可靠 | 否 |
| 可靠 | 尽力而为 | 是 |
| 可靠 | 可靠 | 是 |

### 持久性策略的兼容性

| 发布者 | 订阅 | 是否兼容 | 结果 |
| --- | --- | --- | --- |
| 易失 | 易失 | 是 | 仅接收新消息 |
| 易失 | 本地瞬态 | 否 | 无法通信 |
| 本地瞬态 | 易失 | 是 | 仅接收新消息 |
| 本地瞬态 | 本地瞬态 | 是 | 接收新消息和历史消息 |

要实现对后加入订阅者可见的“锁存”话题，发布者和订阅者双方都必须使用“本地瞬态”。

### 截止时间策略的兼容性

假设 *x* 和 *y* 为任意有效的时长值。

| 发布者 | 订阅 | 是否兼容 |
| --- | --- | --- |
| 默认 | 默认 | 是 |
| 默认 | *x* | 否 |
| *x* | 默认 | 是 |
| *x* | *x* | 是 |
| *x* | *y*（*y* > *x*） | 是 |
| *x* | *y*（*y* < *x*） | 否 |

### 活跃性策略的兼容性

| 发布者 | 订阅 | 是否兼容 |
| --- | --- | --- |
| 自动 | 自动 | 是 |
| 自动 | 按话题手动声明 | 否 |
| 按话题手动声明 | 自动 | 是 |
| 按话题手动声明 | 按话题手动声明 | 是 |

### 租约时长策略的兼容性

假设 *x* 和 *y* 为任意有效的时长值。

| 发布者 | 订阅 | 是否兼容 |
| --- | --- | --- |
| 默认 | 默认 | 是 |
| 默认 | *x* | 否 |
| *x* | 默认 | 是 |
| *x* | *x* | 是 |
| *x* | *y*（*y* > *x*） | 是 |
| *x* | *y*（*y* < *x*） | 否 |

只有所有影响兼容性的策略都兼容，才能建立连接。例如，即使请求配置与提供配置中的可靠性策略兼容，只要持久性策略不兼容，仍然无法建立连接。

如果未建立连接，发布者和订阅之间就不会传递消息。系统提供了检测这种情况的机制，后文将介绍。

<span id="id1"></span>
### 与 ROS 1 的比较

在 ROS 1 中，只要发布者和订阅者使用同一话题和相同的消息类型，就会建立连接。使用 ROS 2 时，需要额外注意请求和提供的 QoS 配置可能不兼容。

<span id="qos-events"></span> <span id="about-qos-qos-events"></span>
## QoS 事件

某些 QoS 策略具有相关事件。开发者可以为每个发布者和订阅设置回调函数，在这些事件触发时按需处理，方式类似于处理话题上收到的消息。

开发者可以订阅以下与发布者相关的 QoS 事件：

- **错过提供的截止时间（Offered deadline missed）**：发布者未能在截止时间策略所规定的预期时长内发布消息。
- **失去活跃性（Liveliness lost）**：发布者未能在租约时长内表明自己仍然活跃。
- **提供的 QoS 不兼容（Offered incompatible QoS）**：发布者发现同一话题上的某个订阅所请求的 QoS 配置，无法由自己提供的 QoS 配置满足，因此两者未建立连接。

开发者可以订阅以下与订阅相关的 QoS 事件：

- **错过请求的截止时间（Requested deadline missed）**：订阅未能在截止时间策略所规定的预期时长内收到消息。
- **活跃性发生变化（Liveliness changed）**：订阅发现所订阅话题上的一个或多个发布者未能在租约时长内表明自己仍然活跃。
- **请求的 QoS 不兼容（Requested incompatible QoS）**：订阅发现同一话题上的某个发布者所提供的 QoS 配置，无法满足自己请求的 QoS 配置，因此两者未建立连接。
