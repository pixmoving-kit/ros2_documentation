# 服务质量设置

<span id="overview"></span>

## 概述

ROS 2 提供了丰富多样的服务质量(QoS)政策,允许您调整节点之间的通信。 有了正确的服务质量政策,ROS 2可以像TCP一样可靠,也可以像UDP那样最佳,在两者之间可能有许多州。 与ROS 1 不同的是,ROS 2 主要是支持TCP,它从基础DDS运输的灵活性中获益,在有失落无线网络的环境中,“最大努力”政策更合适,在实时计算系统中,在满足最后期限需要正确的服务质量配置。

一套QoS“政策”组合组成了QoS“简介 ” 。 鉴于为特定情景选择正确的QoS政策的复杂性,ROS 2为常用案例(例如传感器数据)提供了一套预先定义的QoS简介 。 同时,开发者可以灵活地控制QoS简介的具体政策。

QoS配置可以指定给出版商,订阅,服务服务器和客户端. QoS配置可以独立应用于上述实体的每个实例,但如果使用不同的配置,它们有可能是不兼容的,阻止消息的发送.

<span id="qos-policies"></span> <span id="about-qos-policies"></span>

## 质量保证政策

基础QoS简介目前包括下列政策的设置:

- 历史

  - *保留最后*: 只存储到 N 样本, 通过队列深度选项可配置 。

  - *全部留着*: 存储所有样本,但须遵守基础中间软件的配置资源限制.

- 深度

  - *队列大小*:只有在“历史”政策被确定为“最后”时才感到荣幸。

- 可靠性

  - *尽最大的努力*:试图提供样品,但如果网络不健全,可能会失去样品。

  - *可靠性*:保证样品交付,可以多次重试.

- 重复性

  - *临时本地*: 出版商负责持续进行“晚联”订阅的样本。

  - *挥发*:没有试图使样品具有持久性。

- 截止日期

  - *会期*: 从随后发布的信息到某个主题的预期最长时间

- 寿命

  - *会期*:从发布到接收消息,而不认为消息是 stale 或 过期(过期消息是默默投放的,实际上从未收到)之间的最大时间.

- 活 动

  - *自动*:系统会认为节点的所有出版商在任何一个出版商发表信息时,都会活到另一个 " 租赁期 " 。

  - *按专题分列的手册*:如果(通过给出版商API的电话)手动声称出版商还活着,系统会认为出版商还活着,还有另一个"租期".

- 租赁期限

  - *会期*:在系统认为它失去生命之前,出版商必须表示它还活着的最长时间(失去生命可能是失败的迹象).

对于不是期限的每个政策,还有使用基础中间软件默认的“系统默认 ” 选项。 对于每个属于期限的政策,也存在“默认”选项,这意味着期限未指明,而基础中间软件通常会将其解释为无限长的期限。

<span id="comparison-to-ros-1"></span>

### 与ROS 1的比较

ROS 2中的“历史”和“深度”政策结合在一起,提供了类似于ROS 1中的队列大小的功能。

ROS 2中的“可靠性”政策类似于使用两种UDPROS(仅用于 `roscpp`然而,请注意,即使ROS 2中的可靠政策也是使用UDP实施的,因为UDP允许酌情进行多播。

“持久性”政策“地方性”与任何深度相结合,提供了类似于“拉近”出版商的功能。 ROS 2 中的其余政策与 ROS 1 中的任何政策并不相似,这意味着在这方面,ROS 2 比ROS 1 更具特色。 今后,ROS 2 中甚至会有更多的QoS政策。

<span id="qos-profiles"></span>

## QoS 简介

配置文件允许开发者在不担心每个QoS设置可能的情况下专注于他们的应用. QoS配置文件定义了一组预期在特定使用情况下能够很好地一起运行的政策.

目前定义的QoS配置文件有:

- 出版社和订阅的默认 QoS 设置

  为了让从ROS 1到ROS 2的过渡更加容易,也有必要采取类似的网络行为。 默认情况下,ROS 2的出版商和订阅者对历史的“保存”为“最后 ” , 排队规模为10,“可靠”为可靠性,“挥霍”为耐久性,“系统违约”为生活性。 期限、寿命和租赁期限也都被设定为“违约 ” 。

- 服务

  与出版商和订阅商一样,服务是可靠的。服务使用挥发性耐久性尤为重要,因为否则重新启动的服务服务器可能会收到过时的请求。虽然客户端受到保护,不会收到多个回复,但服务器不会因收到过时的请求而受到影响。

- 传感器数据

  对于传感器数据来说,在大多数情况下,更重要的是及时接收读数,而不是确保所有读数都到达。 也就是说,开发者一旦捕获到最新的样本,就想要这些样本,而可能损失一些样本。 因此,传感器数据简介使用最好的工作可靠性和较小的队列大小。

- 参数

  ROS 2中的参数基于服务,因此具有相似的配置. 不同之处在于参数使用大得多的队列深度,这样当参数客户端无法到达参数服务服务器时,请求就不会丢失.

- 系统默认

  这对所有政策都使用了 RMW 执行的默认值。 不同的 RMW 执行可能有不同的默认值。

[点击这里](https://github.com/ros2/rmw/blob/rolling/rmw/include/rmw/qos_profiles.h) 用于上述简介的具体政策。这些简介中的设置需要根据社区的反馈进行进一步的调整。

<span id="qos-compatibilities"></span> <span id="about-qos-compatibilities"></span>

## QoS 兼容性

**说明:** 本节提及出版商和订阅商,但内容同样适用于服务服务器和客户端.

QoS配置文件可以独立配置给出版商和订阅者。只有在对齐有兼容的QoS配置文件时,才会在出版商和订阅者之间建立联系。

QoS 配置文件的兼容性是根据“请购对出价”模式确定的。 *请求* a QoS简介,即它愿意接受的“最低质量”和出版商 *提议* a QoS 配置是它能够提供的“最大质量 ” 。 只有当所请求的QoS 配置的每项政策不比所提供的 QoS 配置更严格时,才能进行连接。即使所请求的 QoS 配置不同,多个订阅也可以同时连接到一个单一的出版商。出版商和订阅商之间的兼容性不会受到其他出版商和订阅者的影响。

下表显示不同政策设置的兼容性和结果:

*可靠性 QoS 政策的兼容性 :*

| 出版商       | 订阅         | 兼容性 |
|--------------|--------------|--------|
| 尽最大的努力 | 尽最大的努力 | 是     |
| 尽最大的努力 | 可靠性       | 否     |
| 可靠性       | 尽最大的努力 | 是     |
| 可靠性       | 可靠性       | 是     |

*耐久性QoS政策的兼容性:*

| 出版商   | 订阅     | 兼容性 | 结果           |
|----------|----------|--------|----------------|
| 挥发     | 挥发     | 是     | 只发新信件     |
| 挥发     | 临时本地 | 否     | 无来文         |
| 临时本地 | 挥发     | 是     | 只发新信件     |
| 临时本地 | 临时本地 | 是     | 新消息和旧消息 |

为了实现已故订户能够看到的 " 固定 " 专题,出版商和订户必须同意使用 " 本地临时 " 。

*最后期限的兼容性 QoS政策:*

> 假设 *x* 财务报告和财务报告 *y* 是任意有效的持续时间值。

| 出版商 | 订阅                   | 兼容性 |
|--------|------------------------|--------|
| 默认   | 默认                   | 是     |
| 默认   | *x*                    | 否     |
| *x*    | 默认                   | 是     |
| *x*    | *x*                    | 是     |
| *x*    | *y* (何处) *y* \> *x*) | 是     |
| *x*    | *y* (何处) *y* \< *x*) | 否     |

*生活快感政策的兼容性:*

| 出版商           | 订阅             | 兼容性 |
|------------------|------------------|--------|
| 自动             | 自动             | 是     |
| 自动             | 按专题分列的手册 | 否     |
| 按专题分列的手册 | 自动             | 是     |
| 按专题分列的手册 | 按专题分列的手册 | 是     |

*租赁期的兼容性 QoS政策:*

> 假设 *x* 财务报告和财务报告 *y* 是任意有效的持续时间值。

| 出版商 | 订阅                   | 兼容性 |
|--------|------------------------|--------|
| 默认   | 默认                   | 是     |
| 默认   | *x*                    | 否     |
| *x*    | 默认                   | 是     |
| *x*    | *x*                    | 是     |
| *x*    | *y* (何处) *y* \> *x*) | 是     |
| *x*    | *y* (何处) *y* \< *x*) | 否     |

要建立连接,所有影响兼容性的政策必须兼容。例如,即使一个请求和提供的QoS配置对具有兼容的可靠性QoS政策,但它们具有不兼容的耐久性QoS政策,仍然不会建立连接。

在不连接时, 出版商和订阅商之间不会传递任何消息。 有检测这种情形的机制, 将在后面的一节中述及 。

### 与ROS 1的比较

从历史上看,ROS 1中,任何在同一主题上具有相同消息类型的出版商和订阅商都会被连接起来。 请求和提供的QoS配置文件可能不兼容,这是在使用ROS 2时需要意识到的新事物。

<span id="qos-events"></span> <span id="about-qos-qos-events"></span>

## QoS 事件

一些QoS政策可能存在与之相关的事件. 开发者可能向每个出版商和订阅者提供这些QoS事件引发的回调功能,并以他们认为合适的方式处理它们,类似于处理一个话题上收到的消息的方式.

开发者可以订阅下列与出版商相关的QoS事件:

- 未能按期完成

  出版单位未在截止日期QoS政策规定的预期期限内发布信息.

- 失去生命 失去生命

  出版商未能表明其在租赁期内的活性.

- 提供不兼容的QoS

  出版商遇到一个关于同一主题的订阅,请求提供QoS配置图书不能满足的QoS配置图书,导致出版商与该订阅没有关联.

开发者可能订阅下列与订阅相关的QoS事件:

- 错过了要求的最后期限

  订阅未在最后期限 " QoS " 政策规定的预期期限内收到信息。

- 生活变了

  订阅者注意到,一个或多个关于订阅主题的出版商未能表明其在租赁期内是否活泼。

- 请求的不兼容QoS

  订阅遇到了一个在同一主题上的出版商,该出版商提供QoS配置图,不符合要求的QoS配置图,导致订阅商与该出版商之间没有关联.
