# 测试

<span id="why-automatic-tests"></span>

## 为什么是自动测试?

以下是我们为什么要进行自动化测试的很多好理由:

- 你可以更快地对代码进行递增更新。ROS有上百个包,有许多相互依赖性,因此很难预测小的改变可能造成的问题。如果你的改变通过了单位测试,你可以更有信心你没有带来问题 — — 或者至少问题不是你的错。

- 你可以更自信地重构您的代码。 通过单位测试可以验证您在重构代码时没有引入任何错误 。 这样您就可以免于变化的恐惧 !

- 它导致更好的代码设计。 单位测试迫使您写出代码, 以便更容易测试。 这往往意味着您的基本功能和框架是分开的, 这是我们使用ROS代码的设计目标之一 。

- 它们可以防止反复出现的错误(bug regress) 。 为您修复的每个错误写一个单元测试是好的做法。 事实上, 在您修复错误之前写一个单元测试。 这将帮助您精确地,甚至确定地复制错误, 并且更准确地理解问题所在。 因此, 您也会创建更好的补丁, 然后用你的回归测试测试测试来验证错误是否被修复。 这样, 如果代码在稍后被修改,错误就不会被意外重现。 这也意味着让补丁的审核者相信问题已经解决, 并且贡献是高质量的。

- 其他人可以比较容易地研究您的代码(一种自动文档形式 ) 。 很难判断您在修改时是否已经破译了别人的代码。 单位测试是其他开发者验证其修改的工具。 自动测试记录您的编码决定, 并自动向其他开发者通报其违规情况。 因此测试会成为您的代码的文档 — — 不需要在最长时间内阅读文档, 当需要检查时, 测试系统会准确显示读到什么( 测试失败 ) 。 通过写入自动测试, 您会使其他贡献者更快。 这样可以改进整个ROS 项目。

- 如果我们进行自动化单元测试, 成为ROS 的贡献者就容易得多了。 新的外部开发者很难为您的组件做出贡献。 当他们修改代码时, 他们经常在盲目的情况下进行, 受到很多猜测的驱动。 通过提供自动化测试, 你帮助他们完成任务。 他们的修改会立即得到反馈。 更容易为一个项目做出贡献, 而新的贡献者会更容易加入。 他们的首次贡献质量更高, 降低了维护者的工作量。 一个双赢! !

- 自动测试简化了维护程序。 特别是成熟的软件包, 变化较慢, 并且大多需要更新到新的依赖性, 一个自动测试套件有助于非常迅速地确定软件包是否仍然有效。 这样就更容易决定软件包是否仍然得到支持 。

- 自动测试可以扩大连续集成值。 递归测试, 加上基于正常情景的要求测试, 有助于为您的组件进行整体自动化测试。 您的组件比它所依赖的其他 API 的进化要好( CI 服务器可以更好、 更准确地告诉你代码中的问题是什么) 。

写作测试最重要的好处或许是测试让你成为一个好公民。从长远来看,测试会影响质量,这是许多开源项目中公认的做法。 通过写作回归测试,您正在为ROS生态系统的长期质量做出贡献。

<span id="is-this-all-coming-for-free"></span>

## 这都是免费的吗?

当然,从来就没有免费的午餐,为了获得测试的好处,必须进行一些投资。

- 您需要开发一个测试,它有时可能很困难或成本高昂。 有时它也可能是非三角性的,因为测试应该是自动的。 如果测试应该涉及特殊的硬件(它们不应该:尝试使用模拟、嘲笑硬件,或者将测试缩小到一个较小的软件问题)或者需要外部环境,例如人类操作员,那么事情会变得特别毛茸茸的。

- 返回测试和其他自动测试需要保持。 当组件设计发生变化时, 很多测试会变得无效( 例如它们不再编译, 或丢弃与API设计相关的运行时间例外 ) 。 这些测试失败了 , 不仅因为重新设计重新引入错误, 而且因为需要更新到新设计中。 有时,随着更大的重新设计,旧的回归测试应该放弃 。

- 大型测试体需要很长的时间才能运行,这可以增加连续集成服务器的成本.
