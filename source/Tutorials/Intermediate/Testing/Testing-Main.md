# 测试

<span id="why-automatic-tests"></span>

## 为什么要自动化测试？

采用自动化测试有许多充分的理由，以下是其中一些：

- **可以更快地逐步更新代码。** ROS 包含数百个相互依赖的软件包，很难预判一个小改动会造成什么问题。通过单元测试后，你可以更有把握地认为改动没有引入问题，或者至少问题不是由你的改动造成的。
- **可以更有信心地重构代码。** 单元测试通过可用于验证重构没有引入缺陷，让你不必因害怕改动而束手束脚。
- **有助于改善代码设计。** 单元测试促使你编写更容易测试的代码。这通常意味着将底层函数与框架分离，而这正是 ROS 代码的设计目标之一。
- **防止已修复的缺陷再次出现，即缺陷回归。** 每修复一个缺陷，都应为其编写单元测试；最好先写测试再修复。这样有助于准确、甚至确定性地复现缺陷，更准确地理解问题，进而写出更好的补丁，再通过回归测试验证修复。以后修改代码时，就不容易无意中重新引入该缺陷。这也能让补丁审查者更容易确认问题已解决、贡献质量良好。
- **让其他人更容易修改你的代码，相当于自动化的文档。** 修改他人代码时，很难判断是否破坏了原有行为。单元测试为其他开发者提供了验证改动的工具。自动化测试记录了编码决策，并在这些决策被违反时自动通知开发者。因此，测试成为代码文档：大多数时候无须阅读，需要检查时，测试系统会明确指出应查看哪里，也就是失败的测试。编写自动化测试能提高其他贡献者的效率，从而改善整个 ROS 项目。
- **降低参与 ROS 开发的门槛。** 新加入的外部开发者很难为你的组件做贡献，修改代码时往往依靠猜测、缺少明确依据。自动化测试框架能立即反馈改动结果，让参与项目更容易，也方便新贡献者加入。他们首次提交的贡献质量也会更高，从而减轻维护者的工作量，实现双赢。
- **简化维护工作。** 对于已经成熟、变化较少、主要需要适配新依赖的软件包，自动化测试套件能迅速判断软件包是否仍可正常工作，也更容易判断它是否仍受到支持。
- **增强持续集成的价值。** 回归测试与常规场景需求测试共同构成组件的自动化测试集。当组件依赖的其他 API 发生变化时，这些测试能更充分地检验组件；CI 服务器也能更准确地指出代码中出现的问题。

编写测试最重要的好处或许是让你成为负责任的社区成员。测试影响长期质量，也是许多开源项目广泛接受的实践。编写回归测试，就是为 ROS 生态的长期质量作出贡献。

<span id="is-this-all-coming-for-free"></span>

## 这些好处不需要付出代价吗？

当然，天下没有免费的午餐。要获得测试的好处，也需要投入。

- **需要开发测试，这有时困难或成本较高。** 测试必须自动执行，因此并非总是轻而易举。涉及特殊硬件或外部环境（例如人工操作员）时尤其复杂。测试应尽量避免依赖特殊硬件，可以使用仿真、模拟硬件，或将测试范围缩小到更具体的软件问题。
- **回归测试和其他自动化测试需要维护。** 组件设计变化后，许多测试可能失效，例如无法编译，或因 API 设计变化而在运行时抛出异常。这些失败未必意味着重新引入了缺陷，也可能只是测试需要适配新设计。有时进行较大规模的重新设计后，应舍弃旧的回归测试。
- **大量测试可能耗时较长，增加持续集成服务器的成本。**
